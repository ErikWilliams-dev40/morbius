# ADR-0001: Prototype workflow with Helix release authority

- **Status:** proposed
- **Date:** 2026-09-06
- **Deciders:** Helix technical admin and business approver, pending

## Context

Mobius must move new projects and existing-project changes through requests, clickable demos, feedback, and developer handoff. Plan for 26–100 creation/revision requests each week, 1–5 staff, and one active build. External reviewers must verify email and have explicit access. Hermes has not been installed or selected.

## Decision

Keep the prototype workflow separate from production authority. A Workers-compatible API uses D1 for workflow records and R2 for versioned HTML. Prototype approval binds to the current immutable version and digest; a revision clears approval. Human developers complete production code and follow Helix's independent technical review, business signoff, PR, staging, and release pipeline.

Reuse the supplied Helix authentication and project-status logic through the bounded adapters described in [the integration contract](helix-integration.md). Cloudflare identity, company scope, request/build permissions, prototype approval, and technical administration are separate checks. GitHub repository teams and release authority remain in the existing control plane.

The AI adapter can request and store HTML. It has no repository write, shell, purchase, or deployment tools. HTML runs in a sandbox without same-origin permission and with a restrictive CSP. Review the handling of arbitrary HTML before enabling external invitations.

## Alternatives considered

| Option                                            | Disposition                                                                                        |
| ------------------------------------------------- | -------------------------------------------------------------------------------------------------- |
| Hermes runs every company system and release      | Defer; a coordinator may schedule constrained jobs after scope, identity and audit are established |
| Buy Hostinger before the prototype workflow works | Defer pending hosting decision and usage measurements                                              |
| Replace the existing dashboard with this scaffold | Decline as an integration shortcut; keep its established workflow and stack constraints            |
| Browser-only request storage                      | Does not meet durable records, shared queue, or decision history                                   |
| New standalone email authentication               | Avoid duplicating existing Access sign-in; external invitation scope still needs implementation    |

## Consequences

The prepared workflow can be staged after review and configuration. Additional first-release work includes GitHub publication of local records, external invitations, continuous queue scheduling, and live provider/browser verification. D1/R2 are a proposal and may need adapter work if the approved host differs. No live Mobius deployment or service connection exists.
